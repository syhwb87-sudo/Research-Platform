# PRIDE 연구성과 자동산출·검증·누적관리 플랫폼 설계서

> **장기 성과관리·확산 검토 영역 재설계 문서.**
> 이 영역은 일반 KPI Dashboard가 아니라
> **"연구성과 자동산출·검증·누적관리 플랫폼"** 으로 설계한다.
>
> 상위 문서: `PRIDE_Dashboard_Design.md` (전체 IA·6개 활동군 체계) —
> 본 문서는 그 6장(장기성과 관리)을 대체·확장한다.

---

## 0. 재설계 선언 — 왜 플랫폼인가

KPI Dashboard는 "이미 계산된 숫자"를 보여준다.
그러나 이 영역의 진짜 문제는 **숫자가 만들어지는 과정 자체**다.
연구원이 직접 계산한 기대효과는 부서마다 산식이 다르고, 재무실이 검증할 수 없으며,
완료평가 1회 입력으로 끝나 실현 여부를 아무도 모른다.

따라서 이 영역은 성과의 **등록 → 산출 → 검증 → 누적**의 전 과정을 시스템이 관장하는
플랫폼으로 설계하고, Dashboard는 그 플랫폼의 각 단계를 들여다보는 창(窓)으로 정의한다.

### End-to-End 프로세스 (플랫폼의 등뼈)

```
과제종료 ─▶ 완료평가 ─▶ 성과유형 등록 ─▶ 성과발생대상 지정 ─▶ ERP/DW 데이터 자동 매칭
                                                                       │
   ┌───────────────────────────────────────────────────────────────────┘
   ▼
재무성과 자동 산출(Rule Bank) ─▶ 역효과 차감·기여율 적용 ─▶ 재무실 승인 ─▶ 확정
                                                                       │
   ┌───────────────────────────────────────────────────────────────────┘
   ▼
매년 성과 재산출(자동) ─▶ 장기 활용평가(1~5년차) ─▶ 실현성과 누적관리 ─▶ 추적종료
```

핵심 원칙 4가지:

| 원칙 | 의미 |
|---|---|
| **연구원은 산식을 쓰지 않는다** | 연구원은 성과 발생 "대상"만 지정. 산식은 Rule Bank가, 데이터는 ERP가, 계산은 시스템이 |
| **모든 숫자는 역추적 가능하다** | 최종 순재무성과 → 원천 ERP 레코드까지 Data Lineage로 연결 |
| **긍정효과만 세지 않는다** | 역효과(Erosion) 차감과 연구기여율 적용을 산출식에 내장 |
| **1회 입력이 아니라 매년 재산출** | 기술지속년수까지 매년 자동 재계산·활용평가로 누적 관리 |

## 1. 성과관리 패러다임 전환 (As-Is → To-Be)

| 구분 | As-Is (기존) | To-Be (신규) | 해소되는 문제 |
|---|---|---|---|
| 산출 주체 | 연구책임자가 직접 기대효과 계산 | 연구책임자는 **성과 발생 대상만 지정**, 시스템이 자동 계산 | 연구원 역량에 따른 편차 |
| 산식 | 부서별·개인별 상이 | **Rule Bank** 단일 산식 체계 (버전 관리) | 부서별 산식 상이 |
| 데이터 | 근거자료 개별 수집 | **ERP/DW 공식 데이터** 자동 매칭 | 객관성 부족 |
| 검증 | 기술연구원 자체 정량효과 | **재무실 승인** 워크플로 내장 | 재무실 검증 어려움, 성과 인정 어려움 |
| 시점 | 완료평가 시점 1회 입력 | **매년 실적 재산출** + 1~5년차 활용평가 | 실제 사업성과 검증 어려움 |
| 관리 | 개별 문서 | 장기 **누적관리** (Lineage 포함) | 이력·근거 소실 |

> To-Be에서 연구책임자의 역할은 "계산자"에서 **"성과의 목격자(대상 지정자)"** 로 바뀐다.
> 이 역할 전환이 UI 전반의 설계 기준이다: 입력 화면은 산식이 아니라 **대상 선택기**다.

- 기존 14종은 **폐기하지 않는다.** 연구자의 언어(연구효과)와 재무의 언어(재무성과)는 다르므로,
  14종은 "연구효과 분류"로 유지하고 18종과의 **매핑 레이어**를 둔다 (3장).
- a1 완료평가의 기존 14종 데이터는 매핑 테이블을 통해 신체계로 소급 변환 가능하다.

## 3. 연구효과 14종 ↔ 재무성과 18종 매핑

### 3.1 매핑 매트릭스 (대표 매핑)

| 실수율/품질향상 | A-4 주문외 판매감소 · B-6 수율개선 · C-2 클레임 절감 | B-6 |
| 원단위 절감 | B-2 원단위 절감 · B-4 변동가공비 절감 · B-5 단가절감 · B-9 생산량 증가 | B-2 |
| 생산성 향상 | B-9 생산량 증가 · B-8 고정가공비 절감 | B-9 |
| 공정개선 | B-7 공정생략 · B-4 변동가공비 절감 | B-7 |
| 에너지절감 | B-2 원단위 절감(에너지) · B-4 변동가공비 절감 | B-2 |

### 3.2 자동 추천 로직 (성과 등록 시)

```
입력: 과제의 연구효과 유형(a1) + 기술분류 + 활용부서 + 과제명 키워드
       ↓
1) 매핑 매트릭스에서 후보 재무성과 유형 조회
2) 유사 과제 이력 가중치: 같은 기술분류·활용부서에서 과거 승인된 유형에 가점
3) Top-3 추천 + 각 추천의 근거 표시 ("동일 기술분류 승인 12건 중 9건이 B-6")
       ↓
출력: 추천 유형 3개 (연구책임자는 선택만, 변경 시 사유 입력)
```

- 추천 수용률을 KPI로 관리하여 매트릭스를 지속 보정한다 (운영 데이터로 학습).
- "기타" 선택은 재무실 사전협의 플래그가 자동으로 붙는다.

## 4. Rule Bank 체계

**모든 재무성과는 Rule Bank 기반으로 산출한다. 연구원은 산식 작성자가 아니다 — 산식은 시스템이 관리한다.**

### 4.1 Rule 엔티티 정의

| 필드 | 설명 | 예 |
|---|---|---|
| rule_id | 규칙 식별자 | `RB-A1-003` |
| 성과유형 | 18종 코드 | A-1 |
| 세부산식 | 변수 기반 수식 (선언적 DSL) | `(Q_v − Q_b) × CM_ton` |
| 변수 바인딩 | 각 변수의 데이터원천·집계 방법 | Q_v = ERP 판매실적(검증기간), CM_ton = 관리회계 한계이익 |
| 적용기간 | 규칙 유효기간 | 2026-01-01 ~ |
| 버전 | 개정 이력 (v1, v2 …) | v2 (기준기간 정의 변경) |
| 데이터원천 | ERP 모듈/DW 테이블 | SD 판매실적, CO 관리회계 |
| 승인상태 | 초안/재무실 승인/폐기 | 승인 |
| 승인자·승인일 | 재무실 책임자 | — |

### 4.2 대표 산식 3종

```
[A-1 판매량증대]
  성과총액 = (검증기간 판매량 − 기준기간 판매량) × 톤당 한계이익
    · 판매량: ERP 판매실적, 지정 Key(제품군·강종·고객사…)로 필터
    · 기준기간: 과제 착수 직전 12개월 (규칙 버전에 정의)
    · 톤당 한계이익: 관리회계 공식 값 (연구원 입력 불가)

[A-2 판매가격인상]
  성과총액 = (검증기간 FOB − 기준기간 FOB) × 판매량

[B-2 원단위 절감]
  성과총액 = (개선전 원단위 − 개선후 원단위) × 단가 × 생산량
```

### 4.3 운영 규칙

- **버전 불변성**: 산출된 성과는 산출 시점의 rule 버전을 영구 참조한다.
  규칙 개정은 새 버전 생성이며, 기존 산출액은 재계산하지 않는다 (재무 감사 대응).
- **변수 잠금**: 단가·한계이익 등 재무 변수는 재무실만 갱신 가능.
- **투명성**: 사용자는 결과뿐 아니라 산식까지 추적 가능해야 한다 —
  모든 성과 금액 옆에 `[산식 보기]` 버튼, 클릭 시 rule 버전·변수값·원천 스냅샷 표시.

## 5. 자동산출 DX 프로세스 (5 Steps)

Dashboard는 이 프로세스를 단계 진행바(Stepper)로 시각화한다.
사용자는 자신이 어느 단계에 있고, 시스템이 무엇을 대신 해주는지 항상 볼 수 있다.

```
 [Step1 성과 등록] → [Step2 ERP 매칭] → [Step3 자동 산출] → [Step4 보정] → [Step5 누적관리]
   사람(연구원)        사람+시스템          시스템(Rule)       시스템+재무실      시스템(매년)
```

### Step 1 — 성과 등록 (연구책임자)

입력값: **성과유형**(자동 추천 3종 중 선택) · **연구기여율**(%) · **기술지속년수**(년) · **직접발생비**(원)

- 연구기여율은 가이드 밴드 제공 (유형·유사과제 승인 이력 기반 권장범위). 범위 밖 입력은 사유 필수.
- 직접발생비 = 성과 실현을 위해 추가 투입된 비용 (설비 개조비 등).

### Step 2 — ERP 데이터 매칭 (대상 지정)

사용자는 **성과를 발생시킨 대상**을 지정한다. 시스템은 ERP 실적 데이터를 자동 매칭한다.

그룹별 입력 Key 세트:

| 그룹 | 입력 Key |
|---|---|
| A (판매/매출) | 제품군 · 품목 · 강종 · 규격 · 주문두께 · 주문폭 · 고객사 · 용도 · 품질등급 · 판매채널 · 신규고객 여부 · 판매기간 |
| B (원가/생산) | 공장 · 공정 · 품목/원료 코드 · 원단위 항목 · 비용계정 · 설비 · 기준/검증기간 |
| C (비용) | 비용계정 · 부서 · 클레임 유형 · 기간 |

- Key 입력 즉시 **매칭 미리보기**: 해당 조건의 ERP 레코드 건수·기간 커버리지·최근 실적 스파크라인.
- 매칭 0건이면 저장 불가 — "성과는 반드시 회사 공식 데이터 위에서만 성립"이 시스템 규칙.

### Step 3 — 자동 산출

Rule Bank의 해당 유형 산식에 매칭 데이터를 대입하여 **성과총액**을 계산. 산출 근거(변수값·레코드 수·기간)를 스냅샷으로 고정 저장.

### Step 4 — 보정 (역효과·기여율·직접비)

```
순재무성과 = [(성과총액 − 역효과) × 연구기여율] − 직접발생비
```

역효과는 6장 카탈로그에서 해당 항목을 시스템이 제시하고, 금액은 동일하게 Rule 기반 산출.

### Step 5 — 누적관리

- 재무실 확정 후, **매년 검증기간을 갱신하여 자동 재계산** (기술지속년수까지).
- 재산출 결과는 연차별 레코드로 적재되어 장기 활용평가(10장)와 연결.

## 6. 역효과(Erosion) 관리

**모든 성과는 긍정효과만 보지 않는다. 반드시 역효과를 차감한다.**

### 6.1 역효과 카탈로그 (유형별 기본 페어)

| 성과유형 | 대표 역효과 | 산출 방식 |
|---|---|---|
| A-1 판매량 증가 | 기존제품 잠식 (Cannibalization) | 잠식 품목 판매 감소량 × 해당 한계이익 |
| A-2 판매가격 인상 | 판매량 감소 (가격탄력) | 수량 감소분 × 한계이익 |
| A-3 고마진 Mix 확대 | 일반재 판매 감소 | 일반재 감소량 × 일반재 마진 |
| A-4 주문외 판매감소 | 초기 품질비용 증가 | 전환 초기 검사·클레임 비용 증가분 |
| B-3 저가원료 대체 | 품질 저하 보정 비용 | 후공정 처리비 증가분 |
| B-7 공정생략 | 품질 리스크 비용 | 불량률 변동 × 처리비 |

- 등록 유형이 정해지면 시스템이 기본 역효과 항목을 **자동 첨부** — 해제하려면 사유+재무실 확인 필요.
- 역효과 금액도 동일하게 ERP 매칭 + Rule 산출 (수기 입력 금지).

### 6.2 시각화 규칙

- 효과와 역효과는 **항상 한 차트에 동시 표시**: 양방향 막대(효과 ↑ / 역효과 ↓) 또는 워터폴.
- 역효과 미산출 상태의 성과총액은 회색+`역효과 미반영` 배지로 표시하여 확정 금액과 구분.

## 7. 연구기여율과 순재무성과 Waterfall

성과 전체를 연구성과로 인정하지 않는다. 차감의 전 과정을 워터폴로 표준 시각화한다.

```
 억원
 120 ┤ ████ 성과총액 120
 100 ┤      ▼ 역효과 −18
  90 ┤ ░░░░ 102
  70 ┤      ▼ 기여율 70% 적용 −30.6
  60 ┤ ░░░░ 71.4
  50 ┤      ▼ 직접발생비 −6
  40 ┤ ████ 순재무성과 65.4   ← 재무실 승인 대상 금액
```

- 워터폴의 각 막대는 클릭 시 근거로 드릴: 역효과 막대 → 역효과 산출 상세, 기여율 막대 → 기여율 사유·유사과제 밴드.
- 이 차트는 성과 상세·승인 화면·경영 보고에서 **동일한 형태로 재사용**한다 (인지 일관성).

## 8. Data Lineage 모델

### 8.1 추적 체인

```
연구과제 → 성과유형 → 입력 Key → ERP 원천데이터 → Rule Bank(버전) → 성과총액
        → 역효과 → 연구기여율 → 순재무성과 → 재무실 승인 → 장기 활용평가 → 누적 성과
```

- 모든 노드는 `lineage_edge(from_node, to_node, snapshot_id, ts)`로 연결된다.
- **역추적 보장**: 최종 금액 어디에서든 "이 숫자는 어디서 왔는가"를 클릭 한 번으로 소급.
  누적 성과 → 해당 연차 산출 → rule 버전+변수 → ERP 레코드 목록(샘플+건수)까지.
- 스냅샷 원칙: ERP 원본은 변할 수 있으므로, 산출에 쓰인 집계값과 레코드 식별자 목록을
  산출 시점에 스냅샷으로 동결한다. Lineage는 스냅샷을 가리킨다.

## 9. 재무실 승인 Workflow

### 9.1 상태 기계

```
        ┌──────── 보완요청 ────────┐
        ▼                         │
 등록 ─▶ 검토 ─▶ (보완) ─▶ 승인 ─▶ 확정
        │                         ▲
        └── 반려 (사유 필수, 재등록 가능) ──┘
```

| 상태 | 주체 | SLA(권장) |
|---|---|---|
| 등록 | 연구책임자 | — |
| 검토 | 재무실 담당 | 접수 후 10영업일 |
| 보완 | 연구책임자 | 요청 후 5영업일 |
| 승인 | 재무실 책임자 | 검토 완료 후 5영업일 |
| 확정 | 시스템 (연차 재산출 개시) | 즉시 |

- 승인은 **금액 단위가 아니라 산출 체인 단위**: rule 버전·매칭 Key·역효과·기여율을 함께 승인.
- 확정 후 변경은 불가 — 정정은 새 버전 등록(정정 사유 링크)으로만.

## 10. 장기 활용평가 연계

완료평가 이후 1~5년차 장기 추적. 각 연차 평가는 두 개의 축을 기록한다.

| 축 | 값 | 의미 |
|---|---|---|
| **활용상태** | 활용중 / 부분활용 / 미활용 | 기술이 현장에서 살아있는가 |
| **성과상태** | 증가 / 유지 / 감소 / 종료 | 재무성과의 연차 추세 (전년 재산출액 대비) |

- 성과상태는 연차 자동 재산출 결과에서 시스템이 판정한다 (±10% 밴드: 유지).
- **전환율(Realization Conversion)** = 누적 순재무성과 ÷ (승인 시점 연간 순재무성과 × 경과년).
  기대효과 대비 실현효과의 대표 지표로, 코호트·유형·연구소별로 비교한다.
- 미활용 전환 시: 사유코드 + 조치계획 입력이 활용평가 제출 조건.

(활용상태 3값 유지 + 성과상태 4값 추가).

## 13. 구현 로드맵 제안

| 단계 | 범위 | 산출물 |

| **P-1 (Demo 확장)** | Rule Bank 화면·자동산출 워크벤치·워터폴·Lineage를 목업 데이터로 Demo에 추가. 매핑 매트릭스·역효과 카탈로그 시각화 | 시연 가능한 플랫폼 청사진 |

| **P-3 (전면)** | 18종 전체 Rule 등록, 승인 워크플로 가동, 연차 재산출 배치, 기존 a1 데이터 소급 매핑 | 플랫폼 정식 오픈 |

> **P-2를 A그룹부터 시작하는 이유**: 판매 데이터는 ERP 정합성이 가장 높고
> 역효과(잠식) 논의가 명확해, 재무실과의 신뢰를 가장 빨리 쌓을 수 있는 영역이다.
> 이 신뢰가 B·C그룹 확산의 정치적 자본이 된다.
